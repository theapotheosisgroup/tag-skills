# 0005. Versioned skill packages in the Agent Plugins 1.0.0 format, released on GitHub

- **Status:** Accepted; the "No `mcp.json`" decision and the one-package-per-skill rule are superseded by [ADR 0006](0006-mcp-servers-and-agent-packages.md)
- **Date:** 2026-11-22
- **Deciders:** the mission lead (skill updates and versioning, 2026-11-22: approved plan), the tag-skills maintainers (CODEOWNERS)

## Context

Client organizations never maintain skills themselves, and TAG's own agents use the same skills, so TAG must be able to ship skill updates safely. Until now a consumer pinned a commit or a proposed `v*` repository tag and reinstalled; nothing told a harness that an update existed, what changed, or whether it was breaking. The mission lead asked for an update capability with versioning, checked by each harness, using an open plugin standard if one exists, and approved this plan: publish skills as versioned packages in the Agent Plugins 1.0 format, one package per pillar plus the knowledge skills, with semantic versions, a changelog per package, GitHub releases on tag-skills as the registry, and a machine-readable release index that records which skills belong to which plan tier (Foundation, Structure, Turnkey). The updater itself is later work in tag-harness.

### Agent Plugins 1.0.0, as read on 2026-11-22

- Specification: <https://agent-plugins.org/specification>, which reads "Spec Version: 1.0.0", "Status: Published". Some secondary sources still call 1.0.0 a working draft, and the specification repository lists a 1.1.0 working draft (adding hooks). We therefore pin 1.0.0 exactly and ignore 1.1.0.
- Manifest schema: <https://agent-plugins.org/schemas/1.0.0/plugin.schema.json> (served with `Last-Modified: Sat, 21 Nov 2026 02:31:00 GMT`), vendored byte-for-byte at [schemas/vendor/agent-plugins/1.0.0/plugin.schema.json](../../schemas/vendor/agent-plugins/1.0.0/plugin.schema.json), SHA-256 `0a4aad95ce337878ad38802ebf0daa3fde76abe3f65400c86bcbb1ec0b3ab883`. The package check fails if the copy changes. Canonical schema identifiers are never reassigned to different contents (specification section 10.1), so the pin is stable.
- What the format requires: a plugin is a directory with `plugin.json` at its root. The schema is closed: `$schema` (the exact 1.0.0 identifier) and `name` (1-64 characters of `a-z0-9.-`, alphanumeric at both ends, no `--` or `..`) are required; `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords` and `extensions` are optional. `version` is a string that plugins SHOULD make a semantic version and that clients MAY use to detect updates. Client-specific data goes under a reverse-domain namespace in `extensions`. Skills are the immediate children of `skills/` that contain `SKILL.md`; clients do not search deeper. MCP servers go in an optional `mcp.json` at the root.
- What the format leaves out: archives, registries, marketplaces, checksums and update resolution. The specification's design notes treat the directory, not an archive, as the package unit.
- The skill format inside `skills/<name>/` is the [Agent Skills specification](https://agentskills.io/specification), which this repository's validator already enforces ([ADR 0002](0002-node-validator-and-pinned-skills-cli.md), [ADR 0004](0004-pillar-categories-and-prefixes.md)).

## Decision

### Packages

- A package is a release unit defined in `packages/<name>/`, holding only `plugin.json` (an Agent Plugins 1.0.0 manifest) and `CHANGELOG.md` (Keep a Changelog). Skills stay where they are, in `skills/<pillar>/<pillar>-<name>/`; the release script assembles the plugin directory. The repository's `skills/<pillar>/` nesting cannot itself be a plugin, because Agent Plugins only discovers immediate children of `skills/`.
- Packages are named `tag-<id>`: the plugin name must be unique among every plugin a client installs, and a bare `finance` would collide. Skills are not renamed (TrueForge agents reference them by name).
- The packages are `tag-finance` (the 9 `finance-` skills), `tag-governance` (task management, NDA triage, vendor checks, contract review) and `tag-knowledge` (`governance-search-strategy`, `governance-source-management`, `governance-knowledge-synthesis`). The knowledge skills are packaged apart because every pillar uses them (their audiences include `client-finance`), so a Finance-only organization can install them without the contract and NDA skills. They keep their `governance-` names and directory (ADR 0004); package membership is explicit, not derived from the directory.
- `tag-people` is not created until the People pillar has a skill, as with its directory and profile (ADR 0004). The engineering, legal, operations, productivity, data and knowledge category directories of ADR 0003 no longer exist: ADR 0004 removed the engineering and productivity skills and mapped data to `finance-` and legal and knowledge to `governance-`, so there is nothing else to map or exclude.
- Every published skill is in exactly one package. The package check (`npm run packages:check`, part of `test:smoke`) enforces this together with the pinned schema, so a new skill fails CI until it is placed in a package with a tier.
- TAG's data lives in `extensions["com.theapotheosisgroup.tag-skills"]`, validated by [schemas/tag-package.schema.json](../../schemas/tag-package.schema.json): the list of skills, each with the lowest plan tier that includes it. Tiers are cumulative, `foundation` < `structure` < `turnkey`; a skill's tier must be at least the tier of every skill it depends on, in any package. Other clients ignore the namespace, as the specification requires. No other namespace is used.
- `plugin.json` is the source for its version, description, membership and tiers, and it is published unchanged inside the archive. It is validated against the repository (skills exist, each once, dependency tiers, a changelog section for its version), not generated, so nothing is copied by hand from `catalog.json`.
- No `mcp.json`: skills name logical capabilities, which the harness binds with the run's own authorization ([capability contract](../integration/capability-contract.md)); an MCP URL in a package would be a binding, and skills carry no MCP URLs. No `license` field: licences travel per skill (`LICENSE` and `NOTICE.md` in each skill directory), and no single SPDX expression has been established for a package that mixes upstream-derived and TAG-original material.
- Profiles stay as they are: they are install sets for the Skills CLI path, packages are release units.

### Versions

- Packages use Semantic Versioning, starting at `0.1.0`. While the major version is 0, a minor bump is breaking and a patch bump covers features and fixes (SemVer item 4); from `1.0.0`, major is breaking, minor is a feature, patch is a fix. A version once published is immutable.
- A **breaking** change is one that can make an organization lose a skill, need something new, or get an agent that behaves more consequentially without review: a skill removed or moved to another package, a skill's tier raised, a skill's own version bumped as breaking, side effects escalated (`none` < `read` < `draft` < `authorized-write`), invocation changed from `model` to `user`, a newly required capability or input, an output removed, a newly required package or a required range that excludes the previously required versions, or a new Agent Plugins version. A **feature** adds a skill, lowers a tier, adds an output or dependency, or bumps a skill's minor version (from 1.0.0). Anything else that changes a skill is a **fix**. A skill whose content changed since the package's previous release must bump its own `tag-skill.json` version. The full rule, with how to release, is in [packages/README.md](../../packages/README.md#versioning).
- `scripts/release.js build` compares each package with its previous published version in the release index and refuses a version bump too small for the changes it detects. A stable version is compared with the highest lower stable version, so its breaking flag and changes describe the step a `stable`-channel organization takes, and a stable hotfix may ship below a published pre-release. A required range stays as published while the required package's current version satisfies it and the range's lowest version ships every skill the dependent needs; otherwise it moves to the current version, a breaking change. A stable version never requires a pre-release: it takes its range from the required package's highest published stable version, or is refused until that package ships the needed skills in a stable version. Wording changes it cannot classify fall to the skill's own version bump and review.

### Releases and the index

- A package version is released when its `plugin.json` version is not yet in the release index. `.github/workflows/release.yml` runs on every pull request as a dry run (build, versioning rules, verification of the archives with the system `tar`; nothing published) and, on a push to `develop`, publishes each new version as a GitHub release tagged `<package>@<version>` with the archive `<package>-<version>.tar.gz`, the changelog section and detected changes as release notes, and a snapshot of the index. It then replaces `index.json` on the rolling `skills-index` release, at the stable URL <https://github.com/theapotheosisgroup/tag-skills/releases/download/skills-index/index.json>. GitHub releases are the registry, since the format defines none.
- The archive holds one directory, `<package>/`, with `plugin.json`, `CHANGELOG.md` and `skills/<skill>/...`: extracted, it is a conforming plugin. It is reproducible: entries are sorted, timestamps are the commit time, ownership is 0/0, modes are 0644 or 0755, and the gzip header has no timestamp. The same commit gives byte-identical archives on the same Node.js version (pinned in `.nvmrc`); the index records each published archive's checksum, so a later rebuild is never needed.
- The index ([schemas/release-index.schema.json](../../schemas/release-index.schema.json)) lists, for each package, a `stable` channel (the highest version without a pre-release suffix) and every version, newest first, with its tag, commit, date, previous version, whether it is breaking, the detected changes, the minimum Agent Plugins version (`1.0.0`), the archive URL, SHA-256 and size, required packages (`tag-governance` requires `tag-knowledge`), every skill's version, tier, content hash, side effects, invocation, required capabilities and inputs, outputs and dependencies, the skills per tier, and the changelog section. It is built from the previous index plus the new entries, with sorted keys and no clock reads, so the same inputs give the same bytes.
- The `v*` repository tags of the organization's RELEASES standard stay available for whole-repository pins with the Skills CLI; package releases are the update channel.

## Consequences

- A harness can poll one URL, compare an organization's installed package versions with the `stable` channel or its pin, see whether an update is breaking and what it changes before installing it, verify the archive checksum, and install every skill of the package; tiers describe plans and gate nothing, since access is aletia's check on every tool call ([ADR 0006](0006-mcp-servers-and-agent-packages.md)). That updater, the per-organization pins, rolling out to TAG's own organization first, and showing installed version, update availability and changelog are tag-harness work ([integration dependencies](../integration/README.md#dependencies-on-other-repositories)).
- Merging a version bump to `develop` publishes it. The first merge of this change publishes `tag-finance@0.1.0`, `tag-governance@0.1.0` and `tag-knowledge@0.1.0`.
- Contributors bump the package version and add a changelog section to release a skill change; changes merged without a bump stay pending (the dry run lists them) until the next bump.
- The tier assignment in the manifests is the initial one. Moving a skill to a higher tier later is a breaking release.
- A half-finished publish (a tag created without an index entry) stops the next release until a maintainer repairs it ([maintenance guide](../maintenance.md#releases)).

## Alternatives considered

- **Keep repository-wide `v*` tags only.** Rejected: one version for every skill forces every organization to take every change, and says nothing about which skills changed or whether the change is breaking.
- **Vendor-specific plugin manifests** (`.claude-plugin/plugin.json`, Codex or Cursor marketplaces). Rejected: Agent Plugins 1.0.0 is the cross-vendor format, and TAG's harness is the installer.
- **One package per skill.** Rejected for now: 16 release streams for a catalog sold by pillar and tier; skill versions and content hashes in the index already show per-skill change.
- **Knowledge skills inside `tag-governance`.** Rejected: Finance-only organizations would need the governance package for skills every pillar uses.
- **An npm or OCI registry.** Rejected: a new service and credential to run, for files GitHub releases already serve with checksums.
- **Tiers in `tag-skill.json`.** Rejected: tiers are a commercial packaging decision; putting them in the skill would change its content hash and version for a plan change.
- **Committing the index to the repository.** Rejected: the workflow would push to the protected `develop` branch; the index is a release artefact.
